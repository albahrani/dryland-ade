## Workflow graph for next-step routing

Authoritative source: `ask-matt\SKILL.md` (fetched in full from GitHub this session; identical structure to the prior spot-check), cross-checked against each referenced skill's own "When to reach for it" tables (fetched live from aihero.dev for `to-spec`, `to-tickets`, `implement-spec`, `grill-with-docs`, `pr`, `retro`) and each skill's own `SKILL.md` body. No new skills change the graph from the prior research; this is the same graph, restated as edges, now cross-verified against the live aihero.dev prose for several nodes.

**Precondition** (all engineering flows):
- `setup-matt-pocock-skills` → unlocks `to-tickets`, `triage`, `to-spec`, `wayfinder`, `code-review`, `implement-spec` (each explicitly checks for its config and tells the user to run it if missing — e.g. `to-tickets\SKILL.md`: *"The issue tracker and triage label vocabulary should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`."*).

**Main flow edges** (idea → ship):
- `grill-with-docs` (or `grill-me` with no working directory) → [decision reached]
- [decision reached] → `to-spec` (only when work spans multiple sessions; aihero.dev's `to-spec` page table: *"Decided, and the work fits one context window → implement: skip the spec"* vs *"Decided, and the work spans several sessions → `/to-spec`, then `to-tickets`"*)
- `to-spec` → `to-tickets`
- `to-tickets` → `implement` (one ticket at a time) **or** → `implement-spec` (whole spec, parallel subagents, one run)
- `implement` → `tdd` (at pre-agreed seams) → `code-review` (two-axis Standards+Spec)
- `implement-spec` → (per ticket) `tdd` → `code-review` (once, on the integration branch, step 7 of `implement-spec\SKILL.md`)
- [work ready to ship] → `pr` (shapes the PR body; model-invoked automatically per its own description: *"Use when writing a PR body"*, no `disable-model-invocation` flag)
- [after a build] → `retro` (closes the loop; environment/tooling changes, not code)

**On-ramps** (merge onto the main flow):
- [bugs/requests piling up] → `triage` → produces `ready-for-agent` tickets → picked up later by `implement` (never re-triages `to-tickets` output, which is already agent-ready: `triage\SKILL.md` roles section)
- [something's broken] → `diagnosing-bugs` (6-phase loop: feedback loop → reproduce/minimise → hypothesise → instrument → fix+test → cleanup) → `retro` in the same session; "no good seam exists" finding → `improve-codebase-architecture`
- [huge/foggy effort, >1 session] → `wayfinder` (charts a map of decision tickets, resolves one at a time) → `to-spec` once the map clears (aihero.dev `to-spec`/`to-tickets` pages both list: *"A wayfinder map has cleared → `/to-spec #<map_issue>`"* / *"to-spec first, to collapse the map, then `/to-tickets`"*)
- [codebase health, not feature work] → `improve-codebase-architecture` (HTML report of "deepening opportunities") → picking one → `grilling` (+ `domain-modeling`) → feeds into `grill-with-docs`/main flow step 1

**Vocabulary layer** (invoked beneath other skills, not a sequence step):
- `domain-modeling` ← invoked by `grill-with-docs`, `wayfinder`, `triage`, `improve-codebase-architecture`
- `codebase-design` ← invoked by `tdd`, `improve-codebase-architecture`, `setup-ts-deep-modules`
- `grilling` ← the shared interview primitive called by `grill-me`, `grill-with-docs`, `triage`, `wayfinder`, `improve-codebase-architecture`, `loop-me`

**Handoff/continuity edges** (any point in any flow):
- [context window ending / session needs to pass on] → `handoff` or `claude-handoff` (claude-handoff additionally launches a background agent) — both independently reference "suggested skills" the next session should call
- [a message didn't land] → `wait-what` (re-pitch in simplified English using `GLOSSARY.md` vocabulary)

**Standalone/off-main-flow** (user-invoked utilities, no fixed position in the flow): `prototype` (branches into `LOGIC.md`/`UI.md`; referenced as a `grilling`-blocked on-ramp when a question is "ungrollable" per aihero.dev's `grill-me` page), `research` (feeds `grill-with-docs` per the prior inventory), `to-questionnaire` (feeds `grill-with-docs`/`to-spec`), `wizard`, `teach`, `writing-for-agents`, `writing-beats`/`writing-fragments`/`writing-shape` (a self-contained explore→exploit writing pipeline), `loop-me`, `chief-of-staff`, `scaffold-exercises`, `migrate-to-shoehorn`, `setup-pre-commit`, `setup-ts-deep-modules`, `git-guardrails-claude-code`, `grill-me` itself (entry point when there is no working directory at all).

**`wayfinder` internal ticket-type dispatch** (unchanged from prior research): `research` tickets → `research` skill; `prototype` tickets → `prototype` skill; `grilling` tickets (default) → both `grilling` and `domain-modeling`; `task` tickets → manual work, no skill.

## Deterministic vs user-initiated classification

Classification key: **Deterministic** = the skill's own frontmatter disables model-invocation (`disable-model-invocation: true`, meaning it is *never* model-triggered and *only* runs on an explicit slash command or explicit user request) **and/or** its body states a clean, mechanically-checkable artifact-state precondition (an issue/file exists or doesn't). **User-initiated/judgment** = either no clean artifact trigger exists, or the skill is explicitly model-invokable based on fuzzy conversational cues ("the user wants to...") rather than file/git state. Note: `disable-model-invocation: true` by itself speaks to *who* triggers the skill (never the model, always explicit), not to whether a next-step *recommendation engine* could still deterministically suggest it from artifact state — the two axes are independent and both are given below.
