# Decide whether created tickets enter the triage flow

Type: task
Status: resolved

Spec: [spec](../spec.md), user stories 21, 25. ADR 0008. Raised in review of [ticket 24](24-ticket-create-and-resolve.md).

## What to build

Decide what `dryland ticket create` writes for `Status:`, then make it so.

Today it writes no `Status:` line. The tracker reads that as open, so a created ticket appears in `ticket list` and, once unblocked, on `map frontier`. The default skills can read the file. But it carries no triage role, so it sits outside the triage flow until someone labels it.

The options:

- **No status (today).** Created tickets go straight onto the frontier. Simplest, and matches how wayfinder charts tickets.
- **`needs-triage`.** Created tickets wait for triage before an agent picks them up. This needs the role string from `docs/agents/triage-labels.md`, not a literal, and a decision on whether the frontier excludes `needs-triage` tickets.
- **A `--status` option** on `ticket create`, with the first behaviour as default.

Before choosing, check how the default skills (`to-tickets`, `wayfinder`, triage) treat a ticket with no `Status:` line, and which of them create tickets and with what status.

### Agent Brief

**Category:** enhancement
**Summary:** Add an optional `--status` to `dryland ticket create`; with it absent, behaviour is unchanged (no `Status:` line).

**Decision (maintainer):** option 3. Default stays "no status", so created tickets keep going straight onto the frontier as wayfinder expects. `--status` lets a caller put a ticket into the triage flow.

**Desired behavior:**
- `ticket create ... --status <role>` writes `Status: <role string>` using the repo's label string from the triage labels doc, via the existing role vocabulary, never a literal.
- An unknown role fails with an error naming the valid roles.
- Without `--status`, output is identical to today.
- The new-ticket dialog command preview (user story 21) shows `--status` exactly when the command would write it.

## Answer

Decision (maintainer, option 3): ticket create gains an optional --status <role>; absent, it writes no Status line, so created tickets still go straight onto the frontier as wayfinder expects, and --status lets a caller enter the triage flow. The role (or the repo's label for it) goes through resolveTriageRole and the triage-labels doc, so the written line is the repo's label, never a literal; an unknown role fails naming the valid roles with a hint for --status. GitHub/GitLab reject --status as unsupported rather than drop it. The New ticket dialog has a Status select and its command preview shows --status exactly when set.
