# Migration from a skills-only repo

Type: grilling
Status: resolved
Blocked by: 08

## Question

Decide how a repo with .scratch tickets and maps written by the upstream skills moves into the state store: what is imported, what happens to the old files, how forge links and claims carry over, and whether migration is re-runnable. Baseline: the storage decision (event log on a git ref) and the one-way-migration positioning in the map Notes.

## Answer

Decision: migration is an explicit, hands-off command (dryland migrate) with a dry-run preview first; the maintainer makes sure all collaborators have pushed and merged and nothing skill-written is in flight. Preflight requires a clean working tree and only warns about other branches touching .scratch tickets or maps. Mapping: Question becomes the Report; Comments become finding entries; Answer becomes the Solution summary; Type, Status, blocking, ticks, triage roles and map Destination, Notes and fog carry over as structured state; research and prototype files become attachments; Decisions so far is derived and dropped. Every record keeps its verbatim original as an attachment, covering whatever cannot be derived with certainty. Plain feature tickets import as standalone tickets in their triage state; prose files (spec, PRDs) stay in place and are linked from the record. Claims import as open with a note; forge issues import as native tickets linked by URL, then the forge is a reporting channel. Ids are deterministic from the source (map/NN or forge URL), so runs are idempotent and resumable; re-running exists to resume, with no late-arrival import and no banner after finish. Over-cap fields are shortened on import by an agent unslop pass (workflow-triggered rule: applied without per-item acceptance, recorded agent-authored); the original stays as revision 1; a migration report lists old and new per row with a per-ticket diff on demand and one-action revert; a field the pass cannot fix is imported in full and flagged. Safety: working-tree changes go on a dryland-migration branch, one commit per step (remove old ticket and map files, remove or replace upstream skills, install the Dryland prompt set, update agent docs and CLI config); events go to a local-only staging ref refs/dryland/migration with per-step completion records, so a step can be retried or the run resumed; dryland migrate --finish verifies (counts, round-trip comparison against attached originals) and merges the staging ref into the real state ref, then the user merges the branch; --abort deletes branch and staging ref. Migration also removes old skills and agent docs, installs the Dryland prompt set and runs the agent CLI compatibility check (blocks finish only on findings that let an agent bypass the state store; reusable later as dryland doctor), so the repo is workable in Dryland right after finish. Limits: event schema, preflight details, report screens (UX rework) and the exact contents of the prompt set and compatibility checks are left to the spec and tickets 07 and 10; ticket 10 must define what migration installs and removes.
